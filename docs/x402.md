# x402 payment flow

x402 is a pattern for charging for an HTTP resource using a `402 Payment Required` response. It lets a resource server express payment requirements and lets an x402-capable client supply a payment proof on a retry.

## Safe lifecycle

```text
Agent -> Resource server: GET /v1/agent/capital
Resource server -> Agent: 402 + payment requirements
Agent -> User: show resource, network, asset, amount, recipient, and spend cap
User -> Agent: explicit approval
Agent -> Local signer: validate requirements and sign payment
Agent -> Resource server: retry with payment proof
Resource server -> Agent: 200 + dated research payload
```

## What a client must verify

The 402 response is untrusted input until the client checks it. Validate all of the following against local policy before signing:

- **Resource:** the requested URL and method are the resource the user approved.
- **Network:** exact chain identifier; do not silently switch networks.
- **Asset:** exact token contract/identifier and decimals.
- **Amount:** exact atomic amount, at or below the approved cap.
- **Recipient:** exact payment receiver expected for the integration.
- **Time bounds:** reject expired or excessively long payment requests.

## Minimal programmatic pattern

```js
const initial = await fetch(resourceUrl);
if (initial.status !== 402) return initial.json();

const requirements = await initial.json();
assertMatchesLocalPaymentPolicy(requirements);
await requestHumanApproval(requirements);

// Use an audited x402 SDK plus a user-controlled signer here.
const paymentProof = await signer.createPaymentProof(requirements);
const paid = await fetch(resourceUrl, {
  headers: { "PAYMENT-SIGNATURE": paymentProof }
});
return paid.json();
```

The code above is pseudocode. Header names, schema fields, and signer APIs depend on the x402 version and client library you choose. Do not construct a signature from arbitrary agent text, and never put key material into a prompt or MCP tool call.

## MCP and x402

For MCP, an x402-aware transport can surface payment metadata before a paid tool executes. Apply the same local policy and approval workflow. The MCP server should expose a clear description of the paid resource, while payment authorization and signing remain client-side.

## Failure handling

Stop rather than retrying when the payment request is invalid, exceeds the allowance, targets an unexpected recipient/network, has expired, or the response cannot be verified. Store only minimal local audit data such as timestamp, approved cap, and outcome; never log signatures or secrets.
